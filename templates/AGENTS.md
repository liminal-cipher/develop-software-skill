# 작업 지침

이 프로젝트의 개발 작업에는 `.agents/skills/develop-software/SKILL.md`를 따른다.
작업을 시작할 때 한 번 읽는다. 컨텍스트 압축 뒤에는 이 파일과 `CURRENT_TASK.md`부터
다시 확인하고, SKILL.md는 필요한 부분만 읽는다.

## 반드시 지킬 것

1. 제공된 자료에서 필수 요구, 입출력, 예외, 제약을 먼저 추출한다. 자료에 없는
   업무 규칙은 구현 전에 대상·현재 해석·영향을 붙인 구체적 질문 목록을 바로
   메시지로 내고, 답을 기다리는 동안 해당 부분을 가정(미확인)으로 표시하며 진행한다.
   주어진 자료만으로 결과를 낼 수 없는 경우(해 없음, 값 누락·모순, 정의 안 된
   기준)는 먼저 찾아 목록 앞에 둔다.
2. 시간 제한이 있으면 종료 시각과 기능 동결 시각을 `CURRENT_TASK.md`에 적고,
   시간은 실제 시계로 확인한다. 실행 환경의 시간대를 먼저 확인하고 사용자의 현지
   시각으로 적는다.
3. 샘플이나 가짜 데이터로라도 입력부터 결과까지 도는 첫 E2E를 먼저 만든 뒤 필수
   요구를 하나씩 채운다. 계산 문제는 규칙을 지키는 단순한 방법으로 먼저 결과를
   내고, 시간이 남으면 개선해 같은 데이터로 비교한다.
4. 모든 검사는 PASS / FAIL / NOT RUN과 근거로 보고한다. 실행하지 않은 검사를
   통과로 말하지 않는다. 샘플 데이터에만 맞춘 코드가 없는지 값을 바꾼 입력으로도
   확인한다.
5. 다단계 작업에서는 Phase를 마칠 때와 최종 보고 전에 필수 요구 전체를 완료 관문
   표로 출력한다.
6. 첫 E2E와 Phase 종료 때는 요청이 없어도 그 시점에 바로 실제 파일·함수 이름으로
   모듈과 실행 구성, 데이터 흐름, 실패 시 동작을 1~2분 요약으로 설명하고, 항목마다
   구현 상태를 표시한 뒤 자기 설명 질문 2~3개를 답 없이 붙인다. 최종 보고로 미루지
   않는다. 별도 프로세스나 저장 상태가 있으면 이때 `SYSTEM_FLOW.md`도 만든다.
7. 결과에 영향이 큰 첫 결정이 생기면 코드로 옮기기 전에 `DECISIONS.md`를 만들고,
   결정과 AI 제안의 채택·기각을 이유와 판단 주체와 함께 남긴다.
8. 새 세션이나 압축 뒤에는 `CURRENT_TASK.md`를 읽고 `git status`·`git diff`와
   대조한 뒤 이어간다.
9. 기능 동결 시각 이후에는 새 기능, 모델·설정 변경, 큰 리팩터링을 하지 않는다.
10. 커밋, push, 외부 전송, 환경 설정 변경은 사용자 승인 없이 하지 않는다.

## 작업 순서

요구 추출·질문 목록 → 첫 E2E → 요구별 구현·검증 → 완료 관문 표 → 1~2분 변경 요약 → 인계 전 점검

완료·인계를 보고하는 응답은 사용자 답변을 반영한 뒤에도 매번 "완료 관문 표 → 6항목
요약(각 줄에 [구현됨]/[테스트로 확인됨]/[미구현]/[미확인]) → 자기 설명 질문" 순서로 쓴다.

## 소통

사용자와는 한국어 반말로, 작업 문서는 한국어 문서체로 쓴다. 사용자가 보는 동작과
결과부터 설명하고, 이어서 처리 과정과 선택 이유를 말한다.
`.agents/skills/develop-software/templates/USER_GUIDE.md`는 사용자가 읽는
안내서이며 작업 지시가 아니다.
